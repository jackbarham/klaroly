# Engineering audit, 7 September 2026

A read-only audit of `api/` and `app/` for duplication, dead code, comments that should not be there, code that can be reduced without changing behaviour, requests that could be combined, and inconsistency with the conventions this codebase has already written down. Not a security audit and not a feature review. Nothing in the repository was changed by this run except the creation of this file.

## 3. The five findings to do first

1. **F-01, the contacts screen is still on invented data.** `GET /api/contacts` exists and nothing in the app calls it; the store still imports the fixtures file, and the front-end type does not match the resource it would have to read. It is the largest gap between what CLAUDE.md says the app does and what it does, and it is the one thing on this list a user can see.
2. **F-02, seven tests go red for one hour a day in summer.** Any nightly run at that hour reports working code as broken, and the fix is a five-line helper in `Pest.php`.
3. **F-03, the account's day is computed in seven places with six copies of the same paragraph.** The defect this pattern fixes has cost twice already, and F-02 is the third time it has surfaced, on the test side. One method on `Account` ends the series and gives F-02 its helper.
4. **F-04, the eager-load list the waiting-on resolver needs lives in four controllers.** The next relation the resolver reads reintroduces an N+1 on three endpoints at once, and only the endpoint whose query-count test happens to run catches it.
5. **F-05, the money predicates are spelled twice.** The resolver and the attention rows select "an overdue balance" with different code, and a comment is the only thing holding the two together. This is the money path.

Why these rather than the rest: each is either something a user or a CI run can observe today (F-01, F-02) or a duplication on a rule the codebase itself identifies as load-bearing (F-03, F-04, F-05). The remaining findings are real, and most are smaller.

## 5. The data model, if I were starting fresh

These are observations about the schema, the relationships and the query patterns, whether or not a finding above touches them. None is proposed as a change in this audit; the brief puts schema work in its own conversation.

**Two things are called "the main event", and they answer differently.** `Booking::mainEvent()` (`Booking.php:167-170`) is a relation that returns the `main` row or nothing, and `InvoiceNumbering.php:38` reads it to set `balance_due_on`. `ContactActivity::mainEvent()` (`ContactActivity.php:89-95`) falls back to the earliest event, and everything the screens show reads that one. For a standalone trial or a shoot the invoice therefore gets no `balance_due_on` while every list shows the booking under its earliest date. One name for two rules, and the restructure is the place to decide whether a booking with no `main` row has a due date at all.

**One collection, two tie-breaks.** `Booking::events()` orders by `event_date, sort_order` (`Booking.php:164`) and `ContactActivity::byDate()` re-sorts the same loaded collection by `event_date, id` (`:133`). Where a booking has two non-main events on one day the fallback picks by id while a resource iterating `$booking->events` sees `sort_order` first. Harmless today, and one rule when the schema is restructured.

**`payments` and `booking_lines` have no currency column, and every workaround in this codebase exists because of it.** `lines.booking` and `invoices.payments.booking` in five eager-load lists, the `addSelect('bookings.currency')` join in `PaymentsReceived.php:62`, and the fallback chain in `MoneyCast::currencyFor()` (`MoneyCast.php:66-85`). `invoices` and `quotes` already carry a copied `currency`. Copying it onto the two remaining money tables would delete three eager loads, one join select and four "looks redundant and is not" paragraphs, and would make `paidMinor()`'s sum a cast with no relation behind it. Schema section 2 already says every money column sits beside a currency or inherits one; these two inherit through a relation that costs a query.

**The stage groupings are five lists in five files.** `Booking::ENQUIRY_STAGES` (`:49-54`), `EnquiryClashes::HOLDING_STAGES` (`:52-59`), `BookingValue::earnedStages()` (`:201-209`), `SoftHold::classOf()` (`:128-145`) and `HomeController::liveBookings()`'s `whereNotIn` (`:117`), plus the app's `strengthByStage` in `dayMarks.ts`. `SoftHold` is the one that is total over `BookingStage` by construction, a `match` with no default, and `HoldClass.php:13-18` explains why. A stage added to the enum today compiles against `classOf()` and silently falls out of the other four. If the restructure touches stages, a single table of stage properties (holds, is enquiry, is earned, calendar mark) answered by one method each is the shape that cannot drift.

**`bookings.lost_reason` has no check constraint.** Documented and deferred; `LostReason::checkConstraintSql()` is ready and it is the only enum with `HasCheckConstraint` and no migration reading it.

**`invoices` is unique on `(account_id, sequence)` and the factory defaults `sequence` to 1.** Every test that issues two invoices on one account numbers them by hand, four ways (F-19). If sequences were assigned by `InvoiceNumbering` alone and the factory's `issued()` state went through it, the workaround would have nowhere to live.

**The contacts ordering is a correlated subquery, twice.** `ContactController::ordered()` computes next and last activity per contact in SQL and `ContactActivity` computes the same in PHP, held together by a test. A denormalised `next_activity_on` and `last_activity_on` on `contacts`, maintained on event writes, would make the ordering an index scan and delete the second definition; the tradeoff is that every event write becomes a contact write too, which the activity trail in schema 7.8 will want anyway.

**`party_members.event_id` nullable meaning "the main one"** is why `party_size` is the whole booking's and why the home screen draws the party on main events only (`homeList.ts:286-291`). A trial's party is a real number the schema cannot yet hold.

**The `notes` table's `check (booking_id is not null or contact_id is not null)`** is a polymorphic pair without a discriminator. The enquiry detail reads booking notes only and the contact card will read contact notes only, which is fine until a note has to move from one to the other.
